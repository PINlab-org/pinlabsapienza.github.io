# PINlab website

Website of the **Perception and Intelligence Laboratory (PINlab)** at the
Department of Computer Science, Sapienza University of Rome.

The site is built with [Jekyll](https://jekyllrb.com/) and
[Jekyll Scholar](https://github.com/inukshuk/jekyll-scholar). Its current visual
design is adapted from [RT2Lab](https://github.com/rt2lab/rt2lab.github.io), on
top of the original
[Grape Academic Theme](https://github.com/chrjabs/Grape-Academic-Theme).

## Run locally

Ruby 3.4 is used in CI. From the repository root:

```bash
bundle install
bundle exec jekyll serve --livereload
```

Open <http://127.0.0.1:4000>. For a production-style build, run:

```bash
bundle exec jekyll build
```

Do not edit `_site/`; Jekyll regenerates it from the source files.

## Repository map

| Path | Purpose |
| --- | --- |
| `_config.yml` | Site metadata, enabled sections, publication ordering and citation settings |

| `assets/img/projects/` | Project teasers and figures |
| `assets/main.scss` and `assets/css/edo.css` | Site styling |
| `assets/js/` | Publication and project-page interactions |

## Edit site information

General metadata, social links, feature switches and publication grouping live
in `_config.yml`. Homepage research text lives in `index.md`; the homepage hero
structure lives in `_layouts/homelay.html`.

The main navigation is generated by `_includes/navbar.html`. The People,
Publications and Projects links are controlled by the corresponding Boolean
values near the top of `_config.yml`.

## Add or edit a person

People are defined in `_data/people.yml`. Add the photograph to
`assets/img/people/`, then add one item:

```yaml
- people:
  image: /assets/img/people/jane-doe.jpg
  name: Jane Doe
  status: Ph.D. Student
  category: Student
  social:
    webpage: https://example.org
    email: jane.doe@example.org
    orcid: 0000-0000-0000-0000
    scholar: GOOGLE_SCHOLAR_USER_ID
    research_gate: Jane-Doe
    linkedin: https://www.linkedin.com/in/jane-doe/
    github: jane-doe
    twitter: jane_doe
    instagram: jane_doe
```

Use forward slashes in image paths. The supported categories, in display order,
are:

1. `Faculty`
2. `Senior`, displayed as **Senior Collaborators**
3. `Student`, displayed as **Students**
4. `Alumni`

Only non-empty social fields are rendered. GitHub, Twitter, Instagram,
ResearchGate and Google Scholar may use the short account identifier where shown
above. `webpage` and `linkedin` should be complete URLs.

To modify a person, edit the existing YAML item. To move someone between groups,
change only `category`. Check YAML indentation carefully: spaces are significant.

## Add a publication

All papers belong in `_bibliography/publications.bib`. Every entry must have a
unique citation key. Use braced values consistently.

Conference paper:

```bibtex
@inproceedings{doe2026example,
  title = {An Example Conference Paper},
  author = {Doe, Jane and Rossi, Mario},
  booktitle = {Proceedings of the Example Conference},
  year = {2026},
  pages = {10--20},
  doi = {10.1234/example.2026.1},
  url = {https://example.org/paper},
  abstract = {The paper abstract.},
}
```

Journal article:

```bibtex
@article{doe2026journal,
  title = {An Example Journal Article},
  author = {Doe, Jane and Rossi, Mario},
  journal = {Example Journal},
  year = {2026},
  volume = {12},
  number = {3},
  pages = {100--120},
  doi = {10.1234/example.2026.2},
  url = {https://example.org/article},
  abstract = {The paper abstract.},
}
```

arXiv preprint:

```bibtex
@misc{doe2026preprint,
  title = {An Example Preprint},
  author = {Doe, Jane and Rossi, Mario},
  year = {2026},
  eprint = {2601.01234},
  archivePrefix = {arXiv},
  primaryClass = {cs.CV},
  url = {https://arxiv.org/abs/2601.01234},
  abstract = {The paper abstract.},
}
```

The entry type controls the section in which the paper appears:

| BibTeX type | Website section |
| --- | --- |
| `@inproceedings` | Conference |
| `@article` | Journal |
| `@misc` or `@unpublished` | arXiv Preprint |

The Publications page supports these optional link fields:

| Field | Button |
| --- | --- |
| `url` | Paper |
| `doi` | DOI |
| `arxiv` | arXiv |
| `pdf` | PDF; may be a full URL or a filename in `assets/pdf/` |
| `code` | Code |
| `website` | Website |
| `html` | HTML |
| `slides` | Slides |
| `poster` | Poster |
| `supp` | Supplement |
| `blog` | Blog |

Use `abstract` normally. `abstractNote` is also supported for publisher exports
that use that field. Prefer a bare DOI such as `10.1234/example`; do not place a
publisher or indexing-service URL in the `doi` field.

### Validate the bibliography

A successful Jekyll build is not a strict BibTeX check: Jekyll Scholar can
silently rename duplicate keys. Before publishing, run both the Jekyll build and
the standard BibTeX compiler:

```bash
printf '\\relax\n\\citation{*}\n\\bibstyle{plain}\n\\bibdata{%s/_bibliography/publications}\n' "$PWD" > /tmp/pinlab-bibcheck.aux
(cd /tmp && bibtex pinlab-bibcheck)
bundle exec jekyll build
```

BibTeX must finish without errors. Investigate duplicate keys, malformed author
names and conflicting identifiers rather than relying only on the rendered page.

## Add a project website connected to a paper

A connected project uses the **same citation key in three places**:

1. The paper in `_bibliography/publications.bib`.
2. The project page's `citekey` front-matter field.
3. The project card's `citekey` in `_data/projects.yml`.

The bibliography is the source of truth for the visible project title, authors,
venue, year, paper/code buttons, abstract and citation.

### 1. Connect the paper to the page

Add `website` to the paper's existing BibTeX entry. A page name is sufficient:

```bibtex
@inproceedings{doe2026example,
  title = {An Example Conference Paper},
  author = {Doe, Jane and Rossi, Mario},
  booktitle = {Proceedings of the Example Conference},
  year = {2026},
  url = {https://example.org/paper},
  code = {https://github.com/example/project},
  website = {example-project},
  abstract = {The paper abstract.},
}
```

`website = {example-project}` adds the **Website** button to that paper on the
Publications page. A complete external URL is also accepted, but it will not
connect to a local project page.

Project headers use `url`, `code`, `video` and `slides` from this same BibTeX
entry. The `website` field is intentionally not displayed inside the project
page because it would link back to the page already being viewed.

### 2. Create the project page

Create `example-project.md` in the repository root:

```markdown
---
layout: academic-project
title: An Example Conference Paper
description: Project page for An Example Conference Paper
citekey: doe2026example
teaser: /assets/img/projects/example-project/teaser.jpg
teaser_alt: Overview of the proposed method
---

## Method

Project-specific text, figures and videos go here.

## Results

Additional project content goes here.
```

Place its media in `assets/img/projects/example-project/`. With `citekey` set,
the shared `academic-project` layout reads the visible title, authors, venue,
buttons, abstract and BibTeX citation from the matching bibliography entry.

Do not duplicate `abstract` in the page front matter unless the project page
deliberately needs different text. A front-matter `abstract` overrides the
bibliography abstract.

For a media-heavy page, create a specialized layout in `_layouts/` whose front
matter contains `layout: academic-project`, then select that layout in the
project Markdown file. `_layouts/hmu.html` and `_layouts/video-unlearning.html`
are examples. Keep citation metadata in the bibliography rather than embedding
another citation in the specialized layout.

### 3. Add the Projects-page card

Add an item to `_data/projects.yml`:

```yaml
- project:
    title: An Example Conference Paper
    authors: Jane Doe, Mario Rossi
    event: Example Conference
    date: 2026
    citekey: doe2026example
    image:
      path: example-project/teaser.jpg
      alt: Overview of the proposed method
    webpage: example-project
```

For card images, `path` is relative to `assets/img/projects/`. `webpage` must
match the Markdown filename without `.md`, and `citekey` must exactly match the
BibTeX key, including capitalization. The event on the card then links directly
to the corresponding entry on the Publications page.

The card currently stores its display title, authors, event and date in YAML, so
keep those fields synchronized with the bibliography when publication metadata
changes.

## Modify an existing project

- Change citation metadata, links or the abstract in
  `_bibliography/publications.bib`.
- Change card text or its teaser in `_data/projects.yml`.
- Change project-specific content in the corresponding root Markdown file or
  specialized layout.
- Keep the same `citekey` everywhere. If a key changes, update the bibliography,
  project page and project card together.

## Publish

GitHub Actions builds the website whenever `master` is pushed. The generated
site is published to `gh-pages`; do not edit that branch manually. In other
words, after committing a modification on `master`, **you only need to push it**
to make the change live:

```bash
git add -A
git commit -m "Describe the website update"
git push
```

The push starts the **Publish Jekyll to gh-pages** workflow automatically. There
is no separate Jekyll build or deployment command to run for production. Running
`bundle exec jekyll build` locally before the commit is recommended as a check,
but it is not part of the deployment process.

The `old-ui` branch preserves the previous website, while `new-ui2` contains the
development history of the redesign.
